# 双屏点亮原型实测

本记录承接 [双屏调研报告](DUAL-DISPLAY-RESEARCH.zh-CN.md)，对应 2026-09-13、`lhasa`、HyperOS `OS4.0.11.0.XPNCNXM`。本轮运行限时独立原型，未替换当前安装的动画版本。

## 已验证结果

在约 61°、内屏为主屏时，请求状态 `2→5`，分别运行 30 秒和 15 秒后取消请求回到 `5→2`。

| 项目 | 结果 |
| --- | --- |
| 双屏状态 | 请求成功，状态 5 在限时会话中保持 |
| 物理显示状态 | 两块内置屏均为 `ON / committedState ON`；SurfaceFlinger 同时记录两屏 `powerMode=On` |
| 副屏内容 | 预先提交的 OpenGL 彩色网格覆盖外屏，合成器记录可见区域为完整 1168×1712，未被其他图层覆盖 |
| 点亮等待 | 30 秒轮约 190 ms、15 秒轮约 188 ms 后，20 ms 轮询首次读到副屏 ON；不是光学测量的首个可见像素时间 |
| 原主屏状态 | 会话内轮询持续为 ON，进出状态 5 的系统日志仅将逻辑屏幕 1 标为切换中，没有标记主屏 0 |
| 自动恢复 | 取消状态请求、移除试验图层，原单屏控制器和渲染器恢复运行；后续出现状态 2 覆盖请求来自原控制器，属于原有行为 |
| 肉眼观感 | 30 秒轮反馈为“好像没有闪黑”；重复开关后明确确认“确实没有闪黑” |

这证明本机可以在保持内屏为主屏的情况下，用现有 shell 权限让外屏带预置画面进入双屏显示，并正常退出。

## 外屏为主的反向验证

随后保持外屏为主屏，运行状态 6 的限时原型 20 秒。开始时旧控制器覆盖状态为 0；暂停并释放旧控制器后，系统基础状态为 1（TENT），两者均由外屏承担逻辑主屏。实际试验转换为 `1→6→1`，原控制器恢复后再请求状态 0。采集到的铰链角度为约 49°、接触状态为分离。

内屏预先准备 1672×2364 的网格输出，约 251 ms 后轮询首次读到内屏 ON。两块物理显示均确认 `ON / committedState ON`，SurfaceFlinger 的两个物理显示也均为 `powerMode=On`；进入和退出只标记逻辑副屏 1 为切换中。外屏在会话内保持 ON。

对此次反向点亮和关闭，反馈明确为“没有闪黑”。试验结束后已自动取消状态 6、移除试验输出、恢复原控制器与渲染器。

**两个方向的“保持主屏、开启和关闭副屏”均已得到系统证据与肉眼确认。** 后续实时双输出与主屏交换对照结果见下文；尚未完成完整开合流程与高速摄影下严格的零黑帧验收。

## 实时镜像阶段（9 月 13–14 日）

独立原型增加了单源采集、独立副屏输出与双屏动画模式，源码位于 `tools/experiments/`，构建命令和限制见该目录 README。安装中的 APK 及其助手资产未被替换。

第一轮 `live` 运行 30 秒，外屏为主、请求状态 6。约 228 ms 后轮询读到内屏 ON，两块物理显示及 committedState 均为 ON；SurfaceFlinger 确认内屏由试验输出覆盖，虚拟采集输出包含原应用内容。用户确认内屏显示了外屏内容且比例正常，同时指出文字、图标侧转了 90°。日志中约每秒 62 次绘制提交，活动画面期间源帧持续增加，静止画面则减少更新；这些计数不代表端到端延迟测量。

调查发现内屏作为副屏时逻辑 rotation 为 0，之前正常内屏主屏的使用姿态为 rotation 3。试验因此添加了该姿态下的输出旋转补偿，并固定原始 GL 输出的 transform hint 为 0，避免安装旋转导致方形缓冲区的可见裁切位置偏移。第二轮 20 秒镜像约 232 ms 后读到内屏 ON，合成器确认输出 bufferTransform 为 0，自动清理完成。用户明确确认“文字正向，且没有闪黑”。

本阶段的原始证据位于 `build/diagnostics/dual-display-live/`：`trial-live.log`、`trial-live-display.txt`、`trial-live-sf.txt`、`trial-live-oriented.log`、`trial-oriented-sf.txt`。

随后 `fold` 模式运行 30 秒，副屏 ON 首次轮询约为 238 ms。每秒采样记录覆盖约 29°～150° 的开合变化，显示轮询始终为两屏 ON；双输出绘制循环约每秒提交 62 次，结束后原助手均恢复运行。合成器中内、外物理显示各有一个试验输出，虚拟采集显示有 4 个原内容图层、没有试验输出图层，未发现自捕获回路。用户明确确认“一切正常，跟手没闪黑”。原始证据为 `trial-fold.log`、`trial-fold-display.txt`、`trial-fold-sf.txt`。此轮验证保持主屏映射的双屏动画，不代表原生主屏交接或端到端延迟已通过。

## 原生主屏交换对照

在约 45°、外屏为主的姿态运行 20 秒 `handoff` 原型：先进入状态 6，约第 6 秒请求状态 5，让内屏成为真正的系统主屏。显示轮询记录如下，时间相对本轮初始状态 6 请求；状态 1 表示 OFF、2 表示 ON。

| 相对时间 | 事件 |
| --- | --- |
| 6009 ms | 请求状态 5 |
| 6096 ms | 内屏（旧逻辑副屏）state 变为 OFF |
| 6129 ms | 内屏 committedState 变为 OFF |
| 6146 ms | 逻辑主屏已经映射到内屏，两逻辑显示的 state 均为 OFF |
| 6359 ms | 内屏 state 为 ON，committedState 仍为 OFF |
| 6571 ms | 内屏 committedState 为 ON，外屏 state 为 ON、committedState 仍为 OFF |
| 6842 ms | 两屏 state / committedState 均为 ON |

从请求到再次观察到两屏 committed ON 约 833 ms；这不是光学测量的黑屏持续时间。系统日志明确将逻辑显示 0 和 1 同时标为 transitioning，并在 `displays-off=false` 时等待，随后对两块物理屏分别调用 OFF，再调用 ON。对应物理显示电源调用耗时包括内屏 OFF 46 ms、外屏 OFF 224 ms、内屏 ON 206 ms、外屏 ON 174 ms。

这在实机上复现了报告中的系统关屏路径：保持主屏时双屏动画可以连续，交换原生主屏时现有框架仍发出面板关屏请求。预加载纹理、两层遮罩或加快 GL 绘制不能消除这条物理 OFF 路径。要达到完整原生主屏无黑屏交接，需要支持连续切换的系统接口或精确匹配固件的系统改造；当前独立原型未实现这一部分。

原始证据为 `trial-handoff.log`、`trial-handoff-system.txt`。试验已取消覆盖请求并恢复原助手，最终由原控制器按当前姿态决定主屏。

用户要求再试一次后，在约 47°、内屏为主的姿态重复反向对照 `5→6`。第 6001 ms 请求交换，第 6410 ms 轮询到两屏 state / committedState 全部 OFF，第 6838 ms 才再次观察到两屏 committed ON；请求到两屏提交 ON 约 837 ms。系统日志再次记录两屏 transitioning、等待 displays-off、两块物理屏分别 OFF→ON。用户明确确认“会闪黑”。本轮证据为 `trial-handoff-repeat.log`、`trial-handoff-repeat-system.txt`；清理后无试验图层或进程残留，原管理进程、控制器与渲染器已恢复。

## 免 root 补发 ON 对照

在约 54°、外屏为主的姿态，运行 `handoff-on` 20 秒。第 6015 ms 请求状态 5，同时启动仅针对物理内屏的 ON 工作线程，调度窗口 1.25 秒、上限 60 次。实际完成 23 次调用，其中一次阻塞约 490 ms，另一次约 184 ms。SurfaceFlinger 明确记录先接受原系统 OFF，约 50 ms 后接受补发 ON；此后仍发生图层解绑和重新绑定。用户反馈“确实缩短了一点”。

第 7012 ms 才再次轮询到两屏 committed ON，请求到该状态约 997 ms。它比先前单次 833 ms 对照更长，但与主观黑屏缩短并不矛盾：框架完成时间和内屏实际出现画面的时间不是同一个指标；且这不是控制变量充分的统计比较，不能计算可靠改善百分比。

该轮验证了免 root 的物理 ON 指令确实到达 SurfaceFlinger，也否定了“多发 ON 就等同拦截 OFF”的假设。原始证据为 `trial-handoff-on.log`、`trial-handoff-on-system.txt`；试验工作线程停止后取消请求，原助手恢复运行。详细解释见 [免 root 连续切换补充研究](NO-ROOT-DISPLAY-CONTINUITY.zh-CN.md)。

## 按角度提前 ON 与右半屏实时镜像

按用户新要求，`angle-live` 先进入状态 6：外屏主屏，内屏副屏只在正向右半边显示外屏实时内容，左半边黑色。越过配置的 60° 后请求状态 5：内屏主屏，外屏副屏显示内屏右半边。镜像按比例居中裁切铺满，不加入独立过渡快照、模糊或淡入淡出层。原生主屏交换后重建捕获生产者与副屏输出，并等待首帧再显示。

本轮两屏 committed ON 后起步角度约 45°。第 13258 ms、48° 开始串行补发物理内屏 ON；第 13582 ms、60° 请求主屏交换，提前约 324 ms，已完成 19 次 ON。全轮完成 182 次 ON，单次最长阻塞 491 ms；1 ms 是调用完成后的让步间隔，并不意味着每秒能完成 1000 次调用。

第 14225 ms 发现物理映射变化，但系统暂时仍返回旧主屏尺寸；第 14242 ms 更新为内屏 2364×1672，外屏输出 1168×1712。第 14549 ms 新镜像首帧就绪，第 14586 ms 观察到两屏 committed ON；后二者距离交换请求分别约 967 ms、1004 ms，均不能当作光学黑屏时长。随后镜像持续出帧直到限时结束。日志仍记录系统 OFF，不能宣布提前 ON 已消除黑屏。右半屏方位、铺满情况及闪黑主观效果待用户反馈。

用户随后确认铺满正常，但仍会闪黑。因此该轮不能作为无黑屏成功案例。下一步按用户要求，在补发 ON 的同时加入当前画面的 GPU 截图遮罩，单独验证内容重建空档是否能被遮住。

已核对原助手恢复、无试验输出图层残留。证据保存在忽略目录的 `trial-angle-live.log`、`trial-angle-live-system.txt`、`trial-angle-live-display.txt`，未安装新 APK。

此前一次 `angle-on` 在准备阶段因释放旧控制器暴露不同系统基础姿态而退出，未开始 ON 补发，不能用于效果比较。现已在正式宣布就绪前恢复外屏主屏映射，并等待两屏 committed ON。

## 提前 ON 加当前截图遮罩

按用户要求新增 `angle-snapshot`：保持右半屏镜像规则，在预点亮角度将当前捕获帧复制到独立 GPU 纹理，同时为交换前后的两个显示映射预绘制截图层。截图高于实时镜像，并设置排除截图捕获以避免递归。它仍属于正常显示 layer stack，不能越过物理 OFF 或系统空白 stack。

实机一轮：第 14573 ms、48° 开始 ON；第 14623 ms 四个截图输出准备完成；第 14884 ms、61° 请求交换，已提前约 311 ms、完成 18 次 ON。截图早于请求约 261 ms 就绪。第 15516 ms 原子切换到新映射截图，第 15666 ms 新实时镜像首帧就绪，第 15902 ms 两屏 committed ON，第 16273 ms 截图完成淡出。请求到截图淡出约 1389 ms，其中包含等待两屏 ON、至少 200 ms 新帧稳定窗口及 160 ms 淡出，不能等同于黑屏时长。

全轮完成 99 次 ON，单次最长阻塞 506 ms；试验正常结束，原助手已恢复，无截图输出残留。日志证据为 `trial-angle-snapshot.log`、`trial-angle-snapshot-system.txt`。截图仅在显存保存，未导出用户桌面图片。用户确认“闪黑确实缩短了，但是依然可观测”；尚未单独确认截图方向及淡出观感。单次主观反馈不能换算改善百分比，也不能把效果全部归因于截图。

## 原型隔离与两次前置失败（原因）

第一次使用 Canvas 文字绘制时，独立 `app_process` 出现字体初始化 native 断言，发生于状态请求之前。改为 OpenGL 网格后不再触发。

第二次仅持有旧助手的文件锁，副屏在约 190 ms 后 ON、约 812 ms 时又 OFF。旧助手的管理进程会重新启动控制器，而控制器在获取文件锁之前已注册取消状态请求的退出钩子；因此文件锁并不足以隔离请求生命周期。随后将本应用自己的助手管理进程也临时暂停，成功维持两轮双屏会话。正式实现应以单一状态请求所有者与明确会话协议解决，不应把暂停进程作为产品架构。

试验同时使用进程内卡死监测、独立的超时恢复进程、明确的取消与资源释放；不会持续反复发双屏请求去争抢状态。独立恢复仅针对已经核对名称的本应用助手管理进程。限时会话结束后已核对管理进程恢复为正常运行状态。

系统状态采样和图层可见性不能独立证明物理显示不存在极短闪黑；最终仍需肉眼确认或同步拍摄。当前可确认的是双屏呈现能力及同主屏映射下的开关路径，不能据此宣布原生主屏跨屏交接已经无黑屏。
